# Latest security audit follow-up — 20 October 2026

This reviews the supplied [security-audit.md](security-audit.md) against the current application. The original audit is preserved as evidence. Its recommendations were evaluated as findings, not treated as instructions to change product policy or weaken existing protections.

## Finding dispositions

| Audit item | Disposition |
| --- | --- |
| 1. Production configuration | Added a fail-closed startup guard for declared environments other than local/testing. It rejects debug mode, an invalid/non-HTTPS app URL, unsafe session flags, invalid/default application keys, root/empty/short/known-demo database credentials, a test database, invalid trusted origins/proxies, or demo seeding. The development environment example is labeled explicitly. Session security defaults now also cover staging. This does not infer the real hosting environment if an operator incorrectly labels a deployment local/testing. |
| 2. Account-scoped lockout | Retained as a documented security/availability tradeoff. Removing the account-wide limit would weaken distributed password-guess protection. It remains combined with an IP limit and hashed account key, has a short one-minute cooldown, and does not block unrelated accounts. Tests verify key hashing, unrelated-account access, and recovery after cooldown. A risk challenge or alternate recovery path needs a production authentication policy and supporting services; none was invented. |
| 3. Wildcard CORS | Added explicit API CORS configuration using the app origin and explicitly configured additional origins. Wildcards are excluded, required methods/headers are listed, and cross-origin credentials remain disabled. Writes still require the separate trusted Origin/Referer check. The framework's single-origin response may contain its fixed allowed-origin header even for a different request origin; that mismatch grants no browser access. Tests cover single/multiple origins and preflight behavior. |
| 4. Trusted proxies | Added explicit IP/CIDR configuration through PORTAL_TRUSTED_PROXIES. Default is no trusted proxies. Wildcard, REMOTE_ADDR, and /0 trust are rejected. Only client-IP/protocol/port forwarding is trusted from listed peers; forwarded Host is not a trust source. Tests verify both trusted and untrusted peers and HTTPS/HSTS behavior. Actual proxy addresses and the deployed path remain to be validated by the hosting operator. |
| 5. Debug logging | LOG_LEVEL controls logging. Local/testing defaults remain debug; other environments default to warning. Configuration probes cover defaults and overrides. Application code contains no explicit password/token/request-body logger; this is not a full historical log/secret audit or a production retention policy. |
| 6. Unicode CSV prefixes | Extended the first-significant-character check to Unicode control, format, separator and combining-mark prefixes, including BOM, zero-width space, RTL override and variation selectors. Original text is preserved; risky cells receive an apostrophe. CSV round-trip tests cover these prefixes and safe text. Spreadsheet execution itself was not tested. |
| 7. Static SPA CSP | Remains a deployment requirement already documented in the earlier review. Laravel headers do not configure a separate web server/CDN serving frontend HTML. The actual static host must apply and validate the policy; no production host was available and no arbitrary proxy/CDN configuration was invented. |
| 8. Remember me default | Changed to opt-in. Normal sessions still survive navigation/reload; checking the box enables remembered-login restoration. Browser tests verify no recaller by default, explicit opt-in, restoration and logout revocation. The framework recaller duration was not changed; a final lifetime policy remains a deployment decision. Existing users were not forcibly signed out. |
| 9. Tracked test export | Added testing storage to .gitignore and removed only the generated CSV from the index as a staged deletion. Other staged work and Git history were preserved. The original audit identified it as synthetic; no full history rewrite/secret scan was attempted. |
| 10. Transactional notifications | The existing implementation inserts in-app notification rows in the same database transaction as the workflow. It does not dispatch an external worker/email at that point. Ordinary readers cannot observe those uncommitted rows; rollback removes them together with events/version changes. Tests prove outer-transaction rollback and one intended notification on success. Keeping those rows atomic is appropriate; future external delivery must use after-commit dispatch/outbox semantics. |
| 11. Read throttling | Added an account-scoped safe-method budget of 240 reads/minute. It does not consume the separate mutation budget or disrupt normal polling. Tests verify account isolation and that mutations remain usable after exhausting the read budget. This is a configurable guard, not load-test certification. |
| 12. Demo credentials | Existing local/testing seeding gate remains enforced. Non-development startup also rejects DEMO_SEED. The local example is explicitly marked development-only; no production credentials were changed or printed. |

## Implementation and evidence

The main changes are `ProductionConfiguration.php`, `ConfiguredTrustProxies.php`, `config/cors.php`, environment-aware logging/session configuration, the Unicode CSV guard, the read limiter, and the opt-in login checkbox. Six new `LatestAuditTest` regressions plus expanded CSV tests cover the backend changes; the session browser tests explicitly cover the new default.

Startup and logging configuration probes passed. The production guard error identifies unsafe setting names without printing credential values. Direct forwarding tests confirm an untrusted peer cannot supply a different client IP or make an HTTP request appear HTTPS.

The original CORS test assumed an unlisted origin would always receive no allow-origin header. Inspection of the installed framework showed its valid single-origin optimization emits a fixed configured origin. The test now checks that an unlisted origin is never authorized, and also covers the multi-origin branch; no custom workaround was added to alter safe framework behavior.

Final automated results are recorded in [verification](verification.md). Browser tests use the isolated application and database described in [security review](security-review.md); they do not target the working demo.

## Remaining decisions and limits

The account-throttle availability tradeoff, final recaller lifetime, real proxy addresses/TLS path, static-SPA response headers, and database privileges/TLS must be settled or validated before production deployment. They are not evidence of a critical access flaw in the local prototype. No live production penetration test, spreadsheet execution test, distributed load test or full secret-history audit was performed.
